Embun, a glass UI toolkit for Rust

Embun is Indonesian for dew: liquid drops resting on glass. This is the plan for a cross-platform Rust UI toolkit whose glass matches macOS 27 as closely as we can measure, with the first working renderer below.

Loading the renderer… The Rust renderer is fitted to 42 macOS 27.0.1 captures. Turn off "Window has focus" to see glass in a window you aren't using: macOS frosts it more and drops the edge highlight. Rim light and shadow are extras: macOS draws neither on resting controls.

Can it match macOS 27 exactly?

Not pixel for pixel, but close enough that most people can't tell side by side. Apple's shaders and their settings are private, so we rebuild the look from measurements instead of porting code.

The system draws Apple's glass, so it can see the wallpaper and other windows. Ours can only bend what our own app draws. Apple also keeps adjusting the look between point releases, so we freeze one version as the reference: macOS 27.0.1, the version on this Mac.

Where it stands

  • The workspace lives at ~/Development/embun with embun-render, embun-motion, embun and embun-web.
  • embun-render draws frost, lensing, the macOS outline and merging, with rim light and shadow as optional extras. It renders natively on Metal and in the browser through WebAssembly.
  • Phase 0 is done for basic shapes. A capture app puts real macOS 27.0.1 glass over our test backdrops at three slider positions, in light and dark. The first 18 captures turned out to show a window without focus, which looks different, so focused windows were captured again. The shader is fitted to both: average error is 0.9–1.8 out of 255 for focused glass and 0.5–1.1 without focus. Corners use Apple's continuous curve, and merged shapes match the macOS neck within a pixel.
  • Focused glass at the clear setting is mostly the sharp backdrop, bent near the edge, with a thin highlight along the top and bottom. The slider keeps the same 16 pt blur and changes how much of the sharp backdrop shows through. Light glass lets detail brighter than the frost through about twice as strongly as darker detail; dark glass does the reverse.
  • embun-motion has springs with SwiftUI-style response and damping settings.
  • 21 tests pass. Nine render real frames on the GPU: they check glass colors, the outline, the edge highlight and how detail shows through against the macOS captures, and guard against a seam where shapes merge.
  • Real glass buttons are captured too: small and regular buttons are rounded rectangles with a radius of a quarter of their height, larger ones are capsules.
  • Next: tinted glass for prominent buttons, then toolbars, sidebars and menus.

Decisions

Library first, framework later

Ship embun-render as a library that iced, egui and Bevy apps can use. The embun framework comes later, built on top of it.

Tailwind-style styling

Chained methods like .px_4().rounded_full().glass() are the core API. A tw! macro accepts class strings and checks them at compile time.

Freeze macOS 27.0.1

All reference screenshots come from one version. When 27.1 ships, we decide whether to follow it.

Desktop, then web, then mobile

macOS, Windows and Linux first. Web and mobile have the tightest GPU budgets, so they wait until the effect is stable.

Declarative, retained API

Closer to SwiftUI than to egui. Merging shapes need to know which element became which between frames.

Named Embun

"Liquid Glass" is Apple's trademark, so the toolkit has its own name. SF Pro and SF Symbols are licensed for Apple platforms only, so Embun ships open fonts and icons.

Workspace layout

One Cargo workspace, three crates. The two libraries work on their own, and the framework is optional on top of them.

embun-render   library    shapes, frost, lensing, quality tiers (depends only on wgpu)
embun-motion   library    springs and merge transitions (no rendering)
embun          framework  winit + taffy + parley + accesskit, built on the two above

embun-render also compiles to WebAssembly. The prototype on this page gets replaced by the real Rust renderer once Phase 1 is done.

Styling API

Styling works like Tailwind. Layout already follows CSS rules because taffy implements flexbox and grid, so gap, padding and justify-content mean what web developers expect.

Chained methods (the core API)

div()
    .flex().items_center().justify_between()
    .h_13().px_4().gap_4()
    .rounded_full()
    .glass()                  // level 0.5, the macOS 27 default
    .glass_adaptive()         // tint and text color follow the content underneath
    .hover(|s| s.glass_level(0.6))
    .child(icon_button(Icon::Search))

Class strings, checked at compile time

div().class(tw!("flex items-center gap-4 px-4 rounded-full glass glass-adaptive hover:glass-60"))

The tw! macro turns the string into the same method calls while compiling, so a typo is a compile error. Both styles can be mixed.

Components

Phases

Time estimates assume one developer working full time. Each phase has a check that says it's finished.

Phase 0~1 week

Capture the reference

  • On macOS 27.0.1, screenshot the toolbar, buttons, sidebar, menus and sheets over three backgrounds: photos, dense text and a test grid.
  • Take each at three slider positions (ultra clear, middle, tinted) in light and dark. That's 18 shots per control.
  • Build a comparison tool that shows our render next to the screenshot, with a pixel diff and an SSIM score.

Done when any render can be scored against the matching screenshot with one command.

Phase 12–4 weeks

One glass shape, matched

  • Start embun-render: winit and wgpu, a backdrop texture, one rounded rectangle on top. The prototype above is this phase in WebGL2.
  • Build it to WebAssembly as well and swap it into this page's demo.
  • Build the shader in layers: shape, frost, lensing, rim light, tint and saturation, color fringe.
  • Every parameter gets a live slider in an egui debug panel. egui is for tooling only and never ships in the library.

Done when SSIM is 0.95 or higher on all 18 toolbar shots. That threshold is our own target, set to be tightened later.

Phase 23–5 weeks

Renderer architecture

  • A render graph: content layers, then backdrop capture, then the glass pass, then the content that sits on the glass.
  • One blur pyramid per frame, shared by every glass element.
  • All glass shapes drawn in one instanced pass.
  • Glass on glass: one extra backdrop capture per nesting level, with a depth limit.
  • A merge container, our version of Apple's GlassEffectContainer. It blends nearby shapes with a smooth minimum and animates with springs.
  • Damage tracking, so regions that didn't change aren't blurred again.

Done when 20 glass shapes on a 1080p window take under 2 ms of GPU time on an integrated GPU.

Phase 32–3 weeks

Platforms and quality tiers

  • Run on Metal, Vulkan, DX12, WebGPU and WebGL2, using the tiers below.
  • Read each OS's reduce transparency, increase contrast and reduce motion settings.
  • Golden-image tests in CI: render offscreen on each backend and compare to stored images.

Done when the same scene passes golden tests on all five backends.

Phase 46–10 weeks

The embun framework

  • Widget tree, state, event routing, focus and IME, on the crate stack below.
  • Spring animations as the default, since every motion in macOS 27 is spring-based.
  • Text on glass picks its color from the measured backdrop, the same adaptive tint the prototype uses.

Done when a sample settings app runs on macOS, Windows and Linux with screen reader support.

Phase 5Ongoing

Components

Groups 0 to 4 from the components table, in order. Groups 0 and 1 can start alongside Phase 4.

Done when each component passes its Phase 0 screenshot comparison.

The core shader in WGSL

This is the heart of the prototype above, written for wgpu. The shape is a signed distance field. Lensing pushes the sample point inward near the rim, then the frosted backdrop is tinted and lit.

fn sd_round_box(p: vec2f, b: vec2f, r: f32) -> f32 {
    let q = abs(p) - b + vec2f(r);
    return length(max(q, vec2f(0.0))) + min(max(q.x, q.y), 0.0) - r;
}

// Blends two shapes so nearby glass merges like water drops.
fn smin(a: f32, b: f32, k: f32) -> f32 {
    let h = clamp(0.5 + 0.5 * (b - a) / k, 0.0, 1.0);
    return mix(b, a, h) - k * h * (1.0 - h);
}

fn frost(px: vec2f, radius: f32) -> vec3f {
    let lod = max(log2(radius * 0.35), 0.0);
    var acc = vec3f(0.0);
    for (var i = 0u; i < 16u; i++) {
        let f = f32(i);
        let a = f * 2.39996;                       // golden angle
        let r = sqrt((f + 0.5) / 16.0) * radius;
        let uv = (px + vec2f(cos(a), sin(a)) * r) / u.backdrop_size;
        acc += textureSampleLevel(backdrop, samp, uv, lod).rgb;
    }
    return acc / 16.0;
}

fn shade_glass(px: vec2f, d: f32, n: vec2f, appearance: f32) -> vec3f {
    let level = u.glass_level;                     // 0 = ultra clear, 1 = tinted
    let edge = 1.0 - clamp(-d / u.bevel, 0.0, 1.0);
    let lens = -n * pow(edge, 2.2) * u.bevel * 0.9 * mix(1.0, 0.6, level);
    var c = frost(px + lens, mix(3.0, 20.0, level));
    let luma = dot(c, vec3f(0.2126, 0.7152, 0.0722));
    c = mix(vec3f(luma), c, mix(1.45, 1.15, level)); // saturation boost
    let tint = mix(vec3f(0.985), vec3f(0.11), appearance);
    c = mix(c, tint, mix(0.03, 0.8, level));
    let l = dot(n, normalize(vec2f(-0.55, -0.85))); // light from top left
    let rim = smoothstep(1.6, 0.0, -d);
    c = mix(c, vec3f(1.0), rim * (pow(max(l, 0.0), 1.5) * 0.85 + pow(max(-l, 0.0), 1.5) * 0.35));
    return c;
}

Risks

  • Text on glass becomes hard to read. This was the main complaint about macOS 26. Adaptive tint and text color go in during Phase 1, not as a later fix.
  • Blur is expensive on web and mobile. The quality tiers handle it. Measure on a real mid-range phone before promising mobile support.
  • No glass over the desktop. Our glass bends only what our app draws. Transparent windows work differently on each OS, so they stay out of version 1.
  • The reference drifts. Apple may change the look in 27.1 or 28. The freeze in Phase 0 keeps that from becoming endless rework.
  • Phase 4 grows into its own project. That's why the renderer ships first as a crate other UI libraries can use.
